# Framework исследования: dense user×item state поверх TGNv2

> Высокоуровневая карта направлений исследования. Это **не бэклог** — это рамка, из которой
> бэклог вырастает. Конкретные задачи (отдельный `backlog.md`) рождаются как **выход** ранних
> фаз анализа, а не задаются заранее. Документ живой: правим по мере поступления инсайтов.

## 1. Тезис проекта

В `tgbn-*` графах структура **bipartite item–user**, причём item'ов сильно меньше, чем юзеров
(`N_item ≪ N_user`). Малое число item'ов делает доступной **плотную матрицу состояния
`N_user × N_item`**, которая может хранить **per-(user, item) историю взаимодействий**.

Ключ к «живости» идеи — теоретический: TGN **структурно не способен** представить скользящее
среднее по сообщениям (Thm 1 статьи), а именно это эксплуатируют сильнейшие эвристики
(Persistent Forecast / Moving Average). Плотное per-pair состояние — это прямой способ дать
модели то, что TGN выразить не может.

**Гипотеза проекта:** единая (без ансамблей) модель с плотным per-(user, item) состоянием
закрывает разрыв до эвристик над сообщениями/метками, оставаясь обучаемой и обобщающей
— и бьёт TGNv2 как сильнейший *обучаемый* baseline.

## 2. Принципы и ограничения (guardrails)

- **Никаких ансамблей** — в любой форме, включая скрытые (см. `CLAUDE.md`). Плотное состояние
  должно быть **частью единой модели** и кормить единый путь предсказания, а не быть отдельным
  предсказателем, который смешивается с TGN на выходе.
- **CPU-only.** `tgbn-genre` — основной датасет для тестирования гипотез (lighter-конфиг);
  trade/genre/reddit/token на полном Table-2 конфиге — только для измерения качества (см. `CLAUDE.md`).
- **Evidence-gated.** У каждой фазы есть go/no-go gate. Не переходим дальше без подтверждения.
- **Воспроизводимость.** Всё через MLflow (`params`+`tags`), анализ — в ноутбуке (Polars + Plotly, текст на русском).

## 3. Где мы сейчас (Table 1, test NDCG@10) — карта headroom

| | trade | genre | reddit | token |
|---|---|---|---|---|
| **TGNv2** (наш baseline) | 0.735 | 0.469 | 0.507 | 0.294 |
| Moving Avg over messages (M) | 0.777 | 0.472 | 0.411 | 0.415 |
| Moving Avg over labels (L) | 0.823 | 0.509 | 0.559 | 0.508 |

Вывод: **зазор до (L) есть везде**, а на `token` TGNv2 проигрывает даже (M). Это и есть
потенциал, который метод должен забрать. Целевой ориентир — приблизиться к (L)-уровню
*обучаемой* моделью.

## 5. Направления исследования (фазы)

### P0 — Воспроизведение и якорь baseline'ов
- **Цель:** рабочий, измеренный пайплайн; зафиксированная «планка».
- **Действия:** TGNv2 на genre (lighter + full), эвристики (M)/(L), TGN (tuned).
- **Артефакты:** прогоны в MLflow (`experiment=baselines`), таблица «наш baseline vs статья».
- **Gate:** наши числа в разумной близости к Table 1 → иначе чиним пайплайн, прежде чем что-то анализировать.

### P1 — EDA в разрезе user–item («жива ли идея?»)
- **Ключевые вопросы:**
  - Насколько разрежена матрица взаимодействий user×item? Сколько item'ов в среднем «активно» у юзера?
  - Есть ли **temporal autocorrelation** у per-(user, item) ряда весов? (если аффинити «без памяти» — плотная матрица не нужна)
  - **Repeat-структура:** какая доля массы аффинити следующего периода приходится на item'ы, с которыми юзер уже взаимодействовал? (объясняет силу persistent/MA)
  - **Глобальное vs персональное:** что доминирует — популярность item'а (global prior) или персональная компонента?
  - Холодные юзеры/айтемы, нестационарность во времени.
- **Артефакты:** EDA-ноутбук (`experiments/`).
- **Gate:** подтверждена *эксплуатируемая* per-pair структура (autocorrelation + repeat-mass значимо выше global prior) → идея жива; иначе пересматриваем тезис.

### P2 — Диагностика текущего TGNv2 (error analysis в user–item)
- **Ключевые вопросы:**
  - Где TGNv2 теряет NDCG: какие юзеры / айтемы / срезы (cold vs warm, частые vs редкие)?
  - На каких срезах TGNv2 < Moving Avg (M)? Совпадает ли это с тем, что предсказывает Thm 1?
  - Сколько из разрыва до (L) **уже** закрыл source-target identification TGNv2, и сколько осталось?
- **Артефакты:** ноутбук с разложением ошибки по срезам, привязка к MLflow-прогонам.
- **Gate:** локализован конкретный разрыв, который плотное per-pair состояние *в принципе* способно закрыть.

### P3 — Синтез гипотез
- Из P1+P2 → список **фальсифицируемых** гипотез (H1, H2, …). Каждая: что улучшаем, на каком срезе, какой метрикой, ожидаемый эффект.

### P4 — Дизайн метода (dense user×item state)
- Формулировка состояния: **scalar affinity vs D-векторное per-cell** (бюджет памяти учтён, см. §4).
- Правило обновления во времени (decay/EMA / per-cell GRU / learned) и чтения при предсказании.
- **Шов интеграции в код:** `z = z[assoc[n_id]] → node_pred(z)` (`train-tgbn-nodeproppred.py:145-148`), рядом с `MTGNMemory`.
- Проверка guardrail: состояние — часть единой модели, не скрытый ансамбль.

### P5 — Программа экспериментов (зерно бэклога)
- Каждая гипотеза → 1+ эксперимент на genre (lighter-конфиг), go/no-go по NDCG@10 на целевом срезе.
- Здесь framework **перетекает в `backlog.md`**: инсайты P1–P2 + гипотезы P3 нарезаются в конкретные задачи.

### P6 — Масштабирование и измерение
- Лучшие конфиги → полный paper-протокол (3 сида, Table-2) на trade/genre/reddit/token (с поправкой на CPU-выполнимость reddit/token).

### P7 — Абляции, робастность, текст
- Абляция каждого компонента метода; чувствительность к `d`/`x`/seed; оформление в статью (A\*-venue).

## 6. Как инсайты превращаются в бэклог

```
P0 baseline  ─┐
P1 EDA       ─┼─►  инсайты  ──►  P3 гипотезы  ──►  P5 задачи  ──►  backlog.md
P2 диагностика┘
```

Framework = **направления + процесс**. Конкретные задачи (с приоритетом, оценкой, gate) живут в
`backlog.md` и наполняются по мере прохождения P1–P3.

## 7. Открытые вопросы — обсудить вместе

1. **Критерий «живости» в P1.** Какой порог repeat-mass / autocorrelation считаем достаточным подтверждением?
2. **Scalar vs vector per-cell** в P4 — стартуем со scalar (дешевле и буквально воспроизводит moving-average эвристику как частный случай)?
3. **Правило обновления плотной матрицы** — это уже почти метод; фиксируем семейство (decay/EMA/GRU) на старте или держим открытым?
4. **Целевая метрика улучшения** — overall NDCG@10 или конкретный срез (cold users / token)?
5. **Структура бэклога** — отдельный `backlog.md` (предлагаю это) vs раздел внутри framework?
6. **Definition of done для статьи** — какие числа/абляции считаем достаточными для submission?
